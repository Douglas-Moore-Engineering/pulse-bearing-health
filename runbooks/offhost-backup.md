# Automated off-host reference backup

Implemented October 11, 2026 Eastern. The existing half-hour backup service uploads a validated SQLite snapshot to `stpulsebackupb31e9bd1/receipts`, using the VM managed identity. A container-scoped Storage Blob Data Contributor assignment permits access. Anonymous blob and shared-key access are disabled; HTTPS/TLS 1.2 are required. The storage endpoint is network-public but authenticated, not a private endpoint. This is host-loss isolation, not regional disaster recovery or immutable ransomware protection.

The uploader maintains 48 half-hour slots, each capped at 50 MiB. Slot reuse replaces only this backup ring, not primary receipts. Maximum payload is 2,400 MiB, approximately one day's history at regular cadence. Missed runs and clock changes affect retention duration. Versioning/soft-delete must remain disabled for this simple storage bound; introducing them requires a revised retention/cost estimate. Same-identity write/delete privileges are a remaining recovery risk.

Every upload is read back and compared by SHA-256, then restored to an isolated temporary SQLite file for integrity and receipt-count verification. [Executed result](../governance/evidence/azure-offhost-backup.json) recovered 3,150 receipts. Host health requires off-host confirmation and a backup younger than 45 minutes. Status remains stale on a failed upload; the service journal records failure. No external notifications are sent.

The initial attempt failed because container creation was malformed by shell JSON quoting; the corrected file-based request created the container and subsequent upload/readback/restore passed. After the manual starts, the systemd timer ran automatically on October 11 at 9:30 PM Eastern (October 12 01:30 UTC), completing in the next second. Upload, readback and isolated SQLite restoration recovered 3,150 receipts. This establishes one scheduled run; sustained cadence and a complete host-replacement recovery remain unqualified. Offline fault-injection tests cover upload failure, corrupted readback, rejection of invalid SQLite before network access, and successful retry into the same ring slot; they do not establish live outage recovery. One-hour RPO is not claimed solely from timer configuration or one successful snapshot.

Current [retail prices](../governance/evidence/offhost-storage-prices.json): Hot LRS storage $0.0184/GB-month, writes $0.05/10,000 and reads $0.004/10,000. At 48 x 50 MiB maximum retained payload and 1,488 uploads/readbacks per 31-day month, storage plus those transactions is under $0.10/month; reserve $1/month for this bounded reference addition, excluding taxes and exceptional transfer/recovery activity. Prior reference infrastructure estimate was about $80.43/month; the authorized ceiling remains $100, not an enforced billing cap. Monitor actual usage; workload exceeding the 50 MiB snapshot bound fails and requires a revised design.

Configuration and uploader: `infra/single-node/offhost-backup-config.json`, `upload-offhost-backup.py`. The existing `install-backup-timer.sh` installs the orchestrator; `install-health-monitor.sh` refreshes the actual checker executable. No access keys or tokens are stored in the repository.

## Actual Blob-to-container recovery

With explicit renewed Azure verification authorization, `scripts/recover_offhost_snapshot.py` retrieved the latest recorded Blob through the VM managed identity using read-only requests. The snapshot was checksum-verified and written to an ACL-protected ignored private directory, restored into a separate database, and mounted in a network-isolated local container using the default command and configured identity/storage settings. No tokens or database bytes were written to tracked evidence.

[Executed result](../governance/evidence/blob-container-recovery.json): 3,150 receipts, 884 reference windows and one alert survived startup; readiness and SQLite integrity passed. The source lacked the optional reviews table and had zero closures. The first attempt exposed that absent table; the corrected verifier records absence explicitly instead of claiming nonempty history recovery. The temporary container was removed; private snapshots remain available for authorized review. No live database change or new cloud resource occurred. This is actual off-host snapshot recovery into a local application, not complete Azure host replacement, authenticated workflow replay or RTO/RPO qualification.
